# 第一站：`retrieval.py` —— 检索的全部算法

## L1：它在做什么

**四个组件，一条管线：**

```
查询 → BM25（稀疏）  ─┐
     → 向量（稠密）  ─┴→ RRF 融合 → Rerank → Top-K
```

| 组件 | 职责 |
| --- | --- |
| **`tokenize()`** | 中英混合分词：英文按词、中文切 bigram |
| **`BM25`** | Okapi BM25 稀疏检索 |
| **`VectorIndex`** | TF-IDF 加权向量 + 余弦相似度 |
| **`rrf_fuse()`** | Reciprocal Rank Fusion 融合两路排序 |
| **`Reranker`** | 四个可解释特征的交叉重排 |
| **`HybridRetriever`** | 把上面串起来，支持三种 mode |

## L2：三个设计决定

### ① 中文用 **char bigram**，不引入分词器

```python
def tokenize(text):
    ...
    cjk = "".join(_CJK_RE.findall(text))
    for i in range(len(cjk) - 1):
        tokens.append(cjk[i:i+2])      # ★ bigram
    tokens.extend(list(cjk))            # ★ 单字也留一份
```

**为什么**：
- **零依赖**（不用 jieba / pkuseg）
- **召回高**（bigram 覆盖了大部分二字词，不会因为分词错误漏掉）
- **代价**：精度略低，靠 IDF 加权补回来

### ② RRF 而不是加权求和

```python
def rrf_fuse(rankings, k=10, rrf_k=60):
    scores[doc.doc_id] += 1.0 / (rrf_k + rank)
```

**为什么不用 `w1*BM25 + w2*cos`**：

| | 加权求和 | ★ RRF |
| --- | --- | --- |
| 量纲 | ⚠️ BM25 无界正数，余弦 0~1 | ★ 只看**名次**，天然免疫 |
| 调参 | 要精调 `w1/w2` | 几乎无超参 |
| 换数据集 | 权重会失效 | 不用改 |

### ③ Rerank 用**四个可解释特征**

```python
feats["title"]  = len(q_tokens & title_tokens) / len(q_tokens)   # 标题命中率
feats["phrase"] = 最长原样匹配片段 / 6                            # 短语命中
feats["route"]  = 1.0 if doc.route == route else 0.0             # 路由匹配
feats["len"]    = min(len(doc.text)/400, 1.0)                    # 长度（惩罚）
```

**为什么不用模型做 rerank**：**成本 = 每篇一次推理**。这里要的是"便宜且能改正明显错序"。

---

## ★★ L2 的重点：一个**诚实的负面结果**

**消融实验（500 篇库 · 核心 24 条难样本 · Recall@3）：**

| 策略 | Recall@3 |
| --- | ---: |
| 旧：bigram + IDF（第 0 版） | 0.917 |
| **BM25** | ★ **0.958** |
| TF-IDF 向量 | 0.750 |
| **RRF 融合（BM25 + 向量）** | ★ **0.875** ← ★ **比单路 BM25 更差！** |
| RRF + rerank | 0.875 |
| **默认（BM25 单路 + rerank）** | **0.958** |

**★ 融合反而更差。为什么？试着加权看：**

| BM25 权 : 向量权 | Recall@3 |
| --- | ---: |
| 1 : 1 | 0.875 |
| 4 : 1 | 0.875 |
| **8 : 1** | **0.875** |
| **1 : 0（等于纯 BM25）** | **0.958** |

**★ 加权完全无效，直到向量权重归零才恢复。**

### 结论（这段是面试可以讲的）

> **RRF 的分数是 `w/(rrf_k + rank)`，只看名次。**
> **只要某篇文档**只被向量召回**，即使把向量权重压到 1/8，它仍然会挤进 top-k。**
>
> **★ 所以问题不是"排序权重"，是"弱召回路引入了错误候选"。**
>
> **★ 由此得到一条通用原则：**
> **混合检索的前提是「两路各自都有独立价值」。**
> **当一路明显更弱时，用它做**兜底（fallback）**比做**融合（fusion）**更合理。**

**代码里怎么体现这个结论**（`__init__` 的注释 + 默认值）：

```python
def __init__(self, docs, *, mode="bm25", ...):     # ★ 默认 bm25，不是 hybrid
```

**★ 这是"用数据决定默认值"，不是"我觉得混合更高级"。**

## L3：扩展点

| 想加什么 | 改哪里 | 怎么改 |
| --- | --- | --- |
| ★ **换真语义向量** | `VectorIndex` | 换成 embedding 索引，`HybridRetriever(mode="hybrid")` 立刻可用 |
| 调 RRF 的 `rrf_k` | `rrf_fuse(k=...)` | 默认 60 是文献值，调它几乎没用（本实验已验证） |
| 加 rerank 特征 | `Reranker.score()` | 现有 4 个可解释特征，加新特征即可 |
| 加一路检索 | `HybridRetriever.search()` | `rrf_fuse([b, v, your_ranking])` |
| 只对某些 query 走混合 | `search()` 里加判断 | 本实验的结论就是判据：向量弱就别融合 |

## L4：反方案对比

### 反方案 1：直接加权求和而不是 RRF

| | 加权求和 | ★ RRF |
| --- | --- | --- |
| 效果上限 | 可能更高（能利用分数信息） | 略低（丢掉了分数） |
| 调参成本 | 高（要按数据集调） | 几乎为零 |
| ★ **本实验的结论** | 未测 | **RRF 已证明比 BM25 差，问题在召回路不在融合** |

**★ 关键**：**问题不在融合算法，在"向量这一路太弱"。换成真 embedding 后，两者都值得重测。**

### 反方案 2：用 LLM 做 rerank

| | 规则 rerank（选了） | LLM rerank |
| --- | --- | --- |
| 成本 | ~0 | 每篇一次推理 |
| 能改正错序 | ✅（本实验验证） | 更强 |
| 延迟 | μs 级 | 百 ms 级 |

**★ 结论**：**先上免费的规则 rerank，不够再上模型。**

# 第二站：`biz_tools.py` —— 工具的三类性质

## L1：它在做什么

**五个业务工具 + 一个幂等存储：**

| 工具 | 性质 | 关键 |
| --- | :---: | --- |
| `get_customer_history` | 读 | 查客户历史工单 |
| `get_error_code` | 读 | 查错误码字典 |
| `check_service_status` | 读 | 查服务健康（`enum` 约束 4 值） |
| **`create_ticket`** | ★ **写** | ★ **必须传 `idempotency_key`** |
| **`escalate_to_human`** | ★ **高风险** | ★ **不可撤销，需具体理由** |

**★ 为什么要有这一批**：

> **前一批只有 `kb_search`（读）和 `ask_user`（提问）—— 都是**无副作用**的，**
> **试不出工具设计里最要命的问题：**
> **写操作怎么防重复、高风险怎么防误触、工具变多后模型还选得对吗。**

## L2：幂等的三个要点

```python
class IdempotencyStore:
    def run(self, key, fn):
        if key in self._results:
            self.hits += 1
            return self._results[key], True     # ★ 命中：返回第一次的结果
        self.misses += 1
        result = fn()
        self._results[key] = result
        return result, False
```

### ★ 三个必须说清的点

| # | 点 | 为什么 |
| :---: | --- | --- |
| **1** | **键由调用方（Agent）生成** | 服务端只负责去重，不知道"业务意图" |
| **2** | ★ **键必须在重试之间保持不变** | 否则去重失效（每次生成新 key = 每次都是新请求） |
| **3** | ★ **命中时返回第一次的结果** | 不是重新执行，也不能返回"错误"——调用方要拿到同样的结果 |

### 实测（`demo_tools.py` 第 3 段）

```
第 1 次调用：已创建工单 T1001
当前工单数 = 1

第 2 次调用（同 key）：（幂等命中）工单号 T1001
当前工单数 = 1   ← ★ 没有变成 2

第 3 次调用（新 key）：已创建工单 T1002
当前工单数 = 2   ← 这才应该 +1
```

### ★ 双保险设计

```python
# 第一道：注册表的 required 检查
required = spec.parameters.get("required", [])
missing = [k for k in required if k not in arguments]
if missing:
    return ToolResult(ok=False, error=f"bad_arguments: {name} 缺少必填参数 {missing}")

# 第二道：工具自己再查一次（防止有人绕过注册表直接调）
key = str(args.get("idempotency_key", "")).strip()
if not key:
    raise ValueError("idempotency_key 不能为空")
```

**★ 为什么双保险**：**测试要覆盖"绕过注册表"的路径**——因为生产里可能有人直接调工具函数。

## L2 补充：高风险操作的三道闸

| 层 | 做法 |
| --- | --- |
| **描述** | 写「★ 高风险操作，不可撤销」+「不要一遇到不确定就转人工」 |
| **前置校验** | 工单不存在时**直接拒绝**，并列出可用工单号 |
| **返回** | 明确回报「此操作不可撤销」 |

**★ 关键在第 2 条**：**前置校验把"错的输入"变成"可读的错误"，而不是让它去执行一个不可撤销的动作。**

## L3：扩展点

| 想加什么 | 改哪里 |
| --- | --- |
| 加新工具 | 写一个 `make_xxx_tool()`，在 `register_biz_tools()` 里注册 |
| 换真数据库 | 替换 `BizData` 的实现，工具层接口不变 |
| 加幂等过期 | `IdempotencyStore` 加 TTL |
| 加审批流 | 在 `execute()` 前插一个 hook |
| 加工具分组 | `registry` 加 group，按会话挂载 |

## L4：反方案对比

### 反方案 1：让工具自己判断要不要幂等

| | 工具自己判断 | ★ 幂等键（选了） |
| --- | --- | --- |
| 谁知道"这是同一次业务意图" | ❌ 工具不知道 | ✅ **调用方知道** |
| 实现复杂度 | 低 | 中 |

**★ 关键**：**只有调用方知道"这是重试还是新请求"。工具看到的两次调用一模一样，没法区分。**

### 反方案 2：不幂等，靠"先查后写"

```
查有没有这个工单 → 没有 → 创建
```

| 问题 | 说明 |
| --- | --- |
| **竞态** | 两个请求同时"查不到"→ 都创建 |
| **查什么** | 按什么字段查？标题相同但意图不同的怎么办 |

**★ 结论**：**"先查后写"在并发下不可靠；幂等键是唯一可靠的做法。**

### 反方案 3：高风险操作直接禁止，不给工具

**★ 但那就把"能不能转人工"这个业务能力砍掉了。**

**★ 正确做法**：**给工具，但加三道闸。**（就是本实现）

# 第三站：`knowledge_gen.py` —— 为什么手写 + 生成混合

## L1：它在做什么

**在 24 篇手写核心文档上，生成 476 篇长尾文档 → 总共 500 篇。**

**生成规则（确定性、无随机）**：10 个产品模块 × 4 类问题 × 12 个场景。

## L2：为什么要混合

| 只用一种 | 问题 |
| --- | --- |
| **只用手写 24 篇** | 评估太容易（每条 query 都能找到） |
| **只用生成 476 篇** | 语义太模板化，评估太假 |
| ★ **混合** | ★ **接近真实分布：少量核心 + 大量长尾** |

**★ 这正是企业知识库的真实结构。**

## ★ L2 的重点：**另一个诚实发现**

| 评估组 | n | Recall@3 |
| --- | ---: | ---: |
| **核心手写（含同义改写）** | 24 | **0.958** |
| **程序生成（模板拼装）** | 476 | ★ **1.000** |

**★ 生成集接近满分 → 说明这类 query 太容易。**

**原因**：生成的 query 是 `f"{模块}{场景}{锚点}怎么处理"`，**从文档字段直接拼出来的** —— 字面重合度极高。

**★ 结论**：

> **评估集的质量决定评估的价值。**
> **程序生成的 query 不能反映真实难度，需要人工标注 + 同义改写。**

**★ 这条对应笔记 3.4「RAG 评估」里的知识点。**

## L3 / L4

| | |
| --- | --- |
| **L3 扩展点** | 改 `MODULES` 或 `ANCHORS` 自动扩充；加 `doc.metadata` 支持过滤 |
| **L4 反方案** | 不用合成数据 → 那就要人工标注 500 条，成本太高；**合成 + 人工校对**是折中 |

**★ 面试可以讲**：「我用合成数据扩到 500 篇，但**明确标注了合成评估集不可靠**——核心结论只用手写的 24 条。」

# 第四站：实验设计（这次最值钱的部分）

## 为什么"消融实验"比"跑出高分"重要

| 做法 | 能回答什么 |
| --- | --- |
| 跑出一个 Recall=0.95 | 「我的方案大概不错」 |
| ★ **消融实验** | ★ **「哪个组件在起作用、哪个在拖后腿」** |

**★ 本批的消融矩阵（4 个对照）：**

| 编号 | 策略 | 回答什么问题 |
| :---: | --- | --- |
| A | 旧 bigram+IDF | 基线是什么水平 |
| B | BM25 | 换成标准算法能涨多少 |
| C | 向量单路 | 向量这一路本身行不行 |
| D | RRF 融合 | 融合是加分还是减分 |
| E | RRF + rerank | rerank 能不能救回来 |

**★ 结果：B 最好（0.958），D 反而下降（0.875）→ 于是默认用 B。**

## ★ 再一个：为什么分"核心/生成"两组报告

**因为如果把 500 条混在一起算平均：**

$$0.958 \times \frac{24}{500} + 1.000 \times \frac{476}{500} \approx 0.998$$

**★ 高得离谱，但因为 95% 的样本是简单题，这个数字**没有信息量**。**

**★ 分两组报告，才能看出"难样本上到底行不行"。**

# 参考答案要点

| 题 | 要点 |
| :---: | --- |
| ① | tokenize → BM25 + 向量 → RRF 融合 → Rerank |
| ② | `True` = **命中缓存**（此前已处理，未重复执行）；`False` = 首次执行 |
| ③ | 零依赖 + 召回高（bigram 覆盖大部分二字词，不会因分词错误漏召回）；代价是精度略低，靠 IDF 补 |
| ④ | ★ **问题不在融合算法，在向量那一路太弱（0.750）**；RRF 只看名次，弱召回路引入的错误候选**压不下去**（即使权重 1/8 也能挤进 top-k） |
| ⑤ | ★ ① 键由**调用方**生成 ② 键在**重试之间必须不变** ③ 命中返回**第一次的结果** |
| ⑥ | 只改 `VectorIndex`，然后 `HybridRetriever(mode="hybrid")` —— 上层不动 |
| ⑦ | 在 `ToolRegistry.execute()` 里加 hook，或给 `ToolSpec` 加 `needs_confirm` 字段 |
| ⑧ | ★ **不是**。实验证明的是「**我这一路的向量实现太弱**」，不是"混合检索不行"。换成真 embedding 要重测；同时这说明**融合的前提是两路都有独立价值** |
