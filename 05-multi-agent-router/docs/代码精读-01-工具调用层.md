# 第一站：`tools.py` — 工具层

## L1：它在做什么

四个核心概念：

| 概念 | 是什么 |
| --- | --- |
| **`ToolSpec`** | 一个工具的完整定义：名字、描述、参数 schema、执行函数 |
| **`ToolResult`** | 执行结果：成功/失败、内容、错误信息、是否需要用户响应 |
| **`ToolRegistry`** | 工具注册表：注册、生成 schema、执行 |
| **两个工厂函数** | `make_kb_search_tool()` / `make_ask_user_tool()` |

## L2：为什么这样设计（三个决定）

### ① 用**显式 Schema 声明**，不用函数签名反射

```python
ToolSpec(
    name="kb_search",
    description="...",
    parameters={
        "type": "object",
        "properties": {
            "query": {"type": "string", ...},
            "k": {"type": "integer", "minimum": 1, "maximum": 10, "default": 3},
        },
        "required": ["query"],
    },
    func=_run,
)
```

**理由**：参数约束（枚举、范围、默认值）是**语义**，Python 类型注解表达不了。

**而且**：工具定义应该能一眼看出「模型看到的是什么」——反射出来的 schema 要去猜。

### ② 执行**永不抛异常**

```python
try:
    content = spec.func(arguments)
except TypeError as exc:
    return ToolResult(ok=False, error=f"bad_arguments: {name} 参数不匹配（{exc}）")
except Exception as exc:
    return ToolResult(ok=False, error=f"{type(exc).__name__}: {exc}")
```

**理由**：工具失败是**正常业务分支**，不是程序错误。抛异常会中断整个循环，模型就没机会自己改正。

### ③ 错误信息必须**模型可读**

```python
if spec is None:
    available = ", ".join(self.names()) or "（无）"
    return ToolResult(ok=False, error=f"tool_not_found: {name}. 可用工具：{available}")
```

**对比**：

| 错误信息 | 模型能不能改正 |
| --- | --- |
| `"failed"` | ❌ 不知道错在哪 |
| `"参数错误"` | ⚠️ 太笼统 |
| ★ `"bad_arguments: kb_search 缺少必填参数 ['query']"` | ★ ✅ 立刻知道补什么 |
| ★ `"tool_not_found: xxx. 可用工具：kb_search, ask_user"` | ★ ✅ 知道该换成哪个 |

### ★ 为什么 `ask_user` 要做成工具

**代码里看**：

```python
def make_ask_user_tool() -> ToolSpec:
    ...
    return ToolSpec(
        name="ask_user",
        description=(
            "当信息不足以判断、或需要用户确认关键前提时，用它向用户提问。\n"
            "① 只在真正缺少关键信息时使用，不要用它代替思考；\n"
            "② question 要具体，最好一次问清 1-2 个要点；\n"
            "③ 提问后仍需基于已有信息给出可行的初步建议。"
        ),
        ...
        needs_user=True,
    )
```

**理由**：如果只在 system prompt 里写「信息不足就提问」，模型**经常忘了**。

**做成工具之后，「要不要问」变成模型可以主动选择的一个动作**——比写在提示里可靠。

**这就是"给模型行动能力"和"给模型写约束"的区别。**

## L3：扩展点（要加功能就改这里）

| 想加什么 | 改哪里 | 怎么改 |
| --- | --- | --- |
| **新工具** | `tools.py` 加一个 `make_xxx_tool()` 工厂 | 返回 `ToolSpec`，在专家 `make_registry()` 里注册 |
| **加参数校验** | `ToolRegistry.execute()` 里 `required` 检查之后 | 现在只查必填，可加类型/范围校验 |
| **支持并行调工具** | `tool_loop.py` 的 `for call in tool_calls` | 改成 `ThreadPoolExecutor` 并发执行 |
| **工具超时** | 同上 | 给每个 `spec.func` 包一层 `timeout` |
| **工具权限分级** | `ToolSpec` 加 `risk_level` 字段 | 高危工具执行前要求确认 |
| **接 MCP** | `ToolRegistry.to_schema()` + `execute()` | 把这两个方法换成 MCP 客户端的 `tools/list` / `tools/call` |

**★ 最后一行是关键**：**整个 MCP 接入只需要改 `ToolRegistry` 的这两个方法**——因为上层（专家、循环）只依赖这两个接口。

## L4：反方案对比（为什么不用别的做法）

### 反方案 1：从函数签名自动生成 schema

| | 自动反射 | ★ 显式声明（选了） |
| --- | --- | --- |
| 代码量 | 少 | 多 |
| 能表达枚举/范围/默认值 | ❌ | ✅ |
| 一眼看出模型看到什么 | ❌ | ✅ |
| 工具数和函数数解耦 | ❌ | ✅（一个函数可以出多个工具） |

**结论**：工具是**给模型看的接口**，不是内部函数。接口就该显式定义。

### 反方案 2：工具报错就 raise，让上层 catch

| | raise | ★ 转成 ToolResult（选了） |
| --- | --- | --- |
| 模型能自己改正 | ❌（循环已中断） | ✅（错误回填，下一轮改） |
| 实现复杂度 | 低 | 低 |
| 可观测性 | 需要额外 try | 天然（每次调用都有 ok 字段） |

**结论**：**Agent 的核心优势就是"失败后能自己改"，raise 等于放弃这个优势。**

### 反方案 3：把 `ask_user` 写在 system prompt 里

| | prompt 约束 | ★ 做成工具（选了） |
| --- | --- | --- |
| 可靠性 | 模型会忘 | ★ 模型有明确选项 |
| 可观测 | 只能看输出文本 | ✅ 能统计「问了几次」 |
| 可测试 | 难断言 | ✅ `asked_user` 列表可直接断言 |

**结论**：**能做成"动作"的约束，就不要写成"提示"。**

# 第二站：`tool_loop.py` — 工具调用循环

## L1：它在做什么

```
第 1 轮：模型 → 要不要调工具？
   ├─ 不要   → ① 收敛，返回回答
   └─ 要     → 检查是不是重复
              ├─ 重复超限 → ② loop_detected，停止
              └─ 正常     → 执行工具 → 结果回填 → 下一轮
...
轮数用尽 → ③ max_rounds，软着陆（不带工具再问一次）
```

**三个出口，缺一不可。**

## L2：为什么这样设计

### ① 为什么必须有轮数上限

**模型可能陷入**：调工具 → 结果不满意 → 再调同样的工具 → ……

**没有上限的 Agent 在生产环境等于定时炸弹**——它会烧光你的 token 配额，还什么都不产出。

### ② 为什么还要「重复检测」

**轮数上限只能兜住"总次数"，兜不住"一直在做同一件无用功"。**

```python
def _signature(tool_calls) -> tuple:
    return tuple(
        sorted(
            (c.get("name", ""), tuple(sorted((c.get("arguments") or {}).items())))
            for c in tool_calls
        )
    )
```

**两层 `sorted` 各解决一件事**：

| 层 | 解决什么 |
| --- | --- |
| **内层** `sorted(arguments.items())` | `{"a":1,"b":2}` 和 `{"b":2,"a":1}` 是同一个调用（dict 无序） |
| **外层** `sorted(...)` | 多工具调用时顺序不固定，`[调A,调B]` 和 `[调B,调A]` 应视为相同 |

**触发后必须给出可读说明**：

```python
note = f"（检测到重复的工具调用 [{detail}]，已停止。…建议转人工处理。）"
answer = f"{content}\n\n{note}" if content.strip() else note
```

**★ 这里是刻意设计的**：如果模型最后一句是「再查一次」，直接把它当答案返回，用户完全看不懂发生了什么。**必须附上系统侧的说明。**

### ③ 为什么软着陆要「不带工具再问一次」

```python
final = llm.chat_with_tools(msgs, [], temperature=temperature)
```

**`[]` 就是"不许再调工具"的全部实现。**

| 做法 | 结果 |
| --- | --- |
| 直接返回错误 | 用户拿不到任何东西 |
| 截断 messages | 模型失去上下文 |
| ★ **不带工具再问** | ★ **模型只能用已有信息总结** |

## L3：扩展点

| 想加什么 | 改哪里 |
| --- | --- |
| **工具超时** | `registry.execute()` 外层包 timeout |
| **并行执行多工具** | `for call in tool_calls` 改并发 |
| **流式输出** | `chat_with_tools` 换成流式接口，token 逐段回调 |
| **成本统计** | `LoopResult` 加 `tokens_used` |
| **工具调用审批** | 执行前插入「高危工具需确认」的钩子 |
| **从 MCP 加载工具** | 把 `registry` 换成 MCP 客户端适配器（接口不变） |

## L4：反方案对比

### 反方案 1：让模型输出「要不要检索」的布尔字段，代码再决定

| | 布尔字段 | ★ 给工具让它自己选（选了） |
| --- | --- | --- |
| 调用次数 | 固定 2 次（判断 + 生成） | 灵活（模型决定 0–N 次） |
| 多工具场景 | 要加很多字段 | ✅ 天然支持 |
| 实现复杂度 | 低 | 中 |

**结论**：布尔字段只能表达"做/不做一件事"。**要支持多个工具 + 多次调用，就必须是 tool_calls 结构。**

### 反方案 2：固定检索两次（先粗后细）

| | 固定两次 | ★ 模型自主（选了） |
| --- | --- | --- |
| 可预测性 | ✅ 高 | 中 |
| 简单问题成本 | ❌ 浪费一次 | ✅ 0 次 |
| 复杂问题效果 | 可能不够 | ✅ 模型会多查 |
| 可优化 | 调常数 | 调 prompt + 工具描述 |

**结论**：**简单问题占多数时，让模型自己决定"不用查"是实打实的成本节省。**

### 反方案 3：不用 ReAct，直接一次 RAG 生成

| | 一次 RAG | ★ ReAct 循环（选了） |
| --- | --- | --- |
| 延迟 | ✅ 低 | 高（多轮） |
| 需要多次检索的问题 | ❌ 答不好 | ✅ |
| 可解释性 | 中 | ✅ 每步都有记录 |

**结论**：**这是"复杂度换能力"的典型取舍。05 选择 ReAct，是因为它的定位是"演示 Agent 该长什么样"，不是"最低延迟"。**

# 第三站：实测数据（这是第 1 批的另一半产出）

## 检索评估结果

**知识库 24 篇，标注集 24 条**：

| 策略 | n | Recall@3 | MRR | ★ 跨类污染率 |
| --- | ---: | ---: | ---: | ---: |
| **按类检索（路由已知）** | 24 | **0.917** | **0.917** | ★ **0.0%** |
| 全库检索（路由未知） | 24 | 0.917 | 0.917 | ★ **43.1%** |

## ★ 这张表说明了什么

**★ 关键洞察：路由不提升召回，但极大提升上下文纯度。**

- Recall 和 MRR **完全一样**（0.917）
- 但**全库检索时，每 3 篇资料里约有 1.3 篇来自错误类别**
- 按类检索时，这个数字是 **0.00 篇**

**这就是「路由 → 每个专家独立知识库」相比「单 Agent 全库检索」的真实价值**——它不让你找得更全，它让你**给模型的内容更干净**。

# 附：参考答案要点

| 题 | 要点 |
| :---: | --- |
| ① | JSON Schema；类型注解表达不了枚举/范围/默认值，且工具是给模型看的接口，需要显式 |
| ② | 三个：converged（不调工具了）/ loop_detected（重复超限）/ max_rounds（轮数用尽，软着陆） |
| ③ | 工具失败是正常业务分支；抛异常会中断循环，模型失去"自己改正"的机会 |
| ④ | 内层解决 dict 无序；外层解决多调用顺序不固定 |
| ⑤ | `for call in tool_calls` 那一行，改成并发执行 |
| ⑥ | 只需改 `ToolRegistry.to_schema()` 和 `execute()`——上层只依赖这两个方法 |
| ⑦ | 布尔字段只能表达"一件事做不做"；要支持多工具 + 多次调用必须是 tool_calls；且实测简单问题占多数时，"不用查"能省一次调用 |
| ⑧ | ★ 路由不提升召回，**提升上下文纯度**：全库检索 top-3 有 43.1% 是错误类别，按类检索是 0%。干净的上下文降低模型被误导的概率 |
