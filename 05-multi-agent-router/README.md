# 05 · 多智能体路由（Multi-Agent Router）

一个**可运行、零依赖**的多智能体编排最小实现：把工单判给对的专家 Agent。

> 这不是又一个「调用 ChatGPT 的 demo」。
> 它想回答一个工程问题：**多智能体系统里，哪些该让模型决策、哪些必须写死？**

```bash
python examples/demo.py          # 离线跑（MockLLM，不需要 API Key）
python tests/run_all.py          # 52 个测试，全部离线
```

---

## 它做什么

一张用户工单进来，系统判定它属于哪一类，交给对应的专家 Agent 处理：

| 类型 | 专家 | 例子 |
| --- | --- | --- |
| `install` | 安装部署专家 | 「新机器怎么装？要什么环境」 |
| `usage` | 功能使用专家 | 「报表在哪个菜单」 |
| `troubleshoot` | 故障排查专家 | 「报 E1024 进不去」 |
| `fallback` | 通用兜底 | 「你好，有个问题」（信息不足） |

每个专家只拿到**本类**的知识库片段——这是路由相对「单体 Agent 全包」的核心收益。

## 编排图

```
load_memory ──► route ──(条件边)──┬─► expert_install ──────┐
                                  ├─► expert_usage ────────┤
                                  ├─► expert_troubleshoot ─┤
                                  └─► expert_fallback ─────┤
                                                           ▼
                                                       verify ──► remember ──► END
```

| 节点 | 职责 | 是否用 LLM |
| --- | --- | --- |
| `load_memory` | 取客户长期档案 + 本会话历史 | ❌ |
| **`route`** | ★ **判定类别 + 置信度** | ✅ **唯一一处模型决策** |
| `expert_*` | 检索 → 生成回答 → 抽引用 | ✅（生成） |
| `verify` | 检查引用/澄清/异常 | ❌（规则校验） |
| `remember` | 写入两级记忆 | ❌ |

---

## ★ 三个核心设计取舍

### ① 只有 `route` 一处让模型做决策

**为什么**：把「判断」交给模型（灵活，能处理没见过的说法），把「流程」写死（可控、可测、可审计）。

纯自主 Agent 不可控，纯规则系统不灵活——**两者之间的这个点才是生产可用的**。

### ② 置信度低于阈值就兜底，不硬分派

```python
CONFIDENCE_THRESHOLD = 0.7
```

**为什么**：分错的代价 > 承认不确定的代价。低置信度时转 `fallback` 并向用户索取补充信息。

### ③ `verify` 是独立节点，不塞进专家里

**为什么**：**生成和检查是两种能力。** 混在一起时，检查会被"我刚才生成的看起来没问题"这种惯性带偏。

`verify` 用**可判定的规则**（不调 LLM，成本为零）拦住三类问题：
- 非兜底场景**没标注引用** → 疑似编造
- 判定信息不足但**没向用户提问** → 等于没处理
- 上游异常 / 空回答

## 为什么不用 LangGraph

本项目手写了一个 **约 100 行**的状态图引擎（`router_agent/graph.py`）。

**理由**：LangGraph 的核心就是「节点 = `(state) -> update` 的函数」+「边 = 固定或条件跳转」+「一个带步数上限的循环」。**手写一遍之后，再用任何框架都不会被抽象迷惑。**

对应关系：

| LangGraph | 本项目 |
| --- | --- |
| `StateGraph` | `Graph` |
| `add_node` / `add_edge` | `add_node` / `add_edge` |
| `add_conditional_edges` | `add_conditional` |
| `compile()` | 无需编译 |
| `invoke()` | `run(state, max_steps=20)` |

**步数上限是必需的**：条件边可能成环，没有上限就会挂死（测试里专门覆盖了这条）。

## 知识库检索为什么是简化版

真实生产系统用「向量 + BM25 混合检索 + Rerank」。本项目用的是**字符二元组 + IDF 加权**。

**不是偷懒，是取舍**：
1. 零依赖 —— clone 下来零配置就能跑
2. **结果可解释** —— 每一分都能说清是哪几个 bigram 贡献的，便于写测试

升级路径很明确：把 `KnowledgeBase.search()` 换成混合检索即可，**上层专家 Agent 的接口不需要改**。

## 两级记忆

| 层 | 生命周期 | 用途 |
| --- | --- | --- |
| **会话记忆** | 随会话（`session_id`） | 多轮对话的上下文 |
| **客户档案** | 跨会话（按 `customer`） | 「这个客户上次问过同样的问题」 |

**为什么分开**：塞进同一个容器会导致 —— 要么短期记忆被长期污染，要么长期记忆被会话清空。

持久化留了 `Store` 接口，默认内存实现；接 SQLite/Redis 只需换一个实现。

## 关于「和实习项目的关系」

作者 2026 年在杭州某 AI 公司实习时，做的是**真实业务的多智能体销售系统**（LangGraph 编排 + 指挥官路由 + 三个专家 + RAG + 两级记忆）。

**公司代码不能开源**，所以这里用**虚构的技术支持工单场景**，把同一套架构**重新实现了一遍**。

两者的对应：

| 实习项目（不可开源） | 本项目（可开源） |
| --- | --- |
| 售前 / 售中 / 售后路由 | 安装 / 使用 / 故障路由 |
| 销售领域知识库 | 虚构产品文档 |
| 置信度阈值 + 兜底 | 相同机制 |
| LangGraph | 手写状态图（为了讲清本质） |

## 文件结构

```
05-multi-agent-router/
├── router_agent/
│   ├── state.py          # 状态与数据结构（dataclass，字段拼错会报错）
│   ├── graph.py          # 手写状态图引擎（节点/固定边/条件边/步数上限）
│   ├── llm.py            # LLM 接口 + MockLLM + OpenAI 兼容客户端（urllib，零依赖）
│   ├── knowledge.py      # bigram + IDF 检索（可解释）
│   ├── router.py         # 路由节点（唯一用模型做决策的地方）
│   ├── experts.py        # 四个专家 Agent + 引用抽取
│   ├── memory.py         # 两级记忆
│   └── orchestrator.py   # 组装图 + 校验 + 示例知识库
├── tests/run_all.py      # 52 个离线测试
└── examples/demo.py      # 演示（离线 / --real）
```

## 测试覆盖什么

**52 个测试，全部离线**，重点在**编排逻辑**而不是模型质量：

| 组 | 覆盖 |
| --- | --- |
| 图引擎 | 固定边、条件边、成环截断、未知节点报错、未知状态字段报错 |
| 路由 | 正常分派、低置信度兜底、非法 JSON 降级、未知类别降级、置信度夹紧、围栏/夹带文字解析 |
| 检索 | 分类约束、排序正确、空查询 |
| 记忆 | 长期档案、会话隔离、上限截断 |
| 端到端 | 节点顺序、引用抽取、校验失败场景、多轮历史、乱答不崩溃 |

## 扩展点（面试常被问「怎么继续做」）

| 想加什么 | 改哪里 |
| --- | --- |
| 新增一类专家 | 继承 `ExpertBase`，写 `config`，注册进 `EXPERTS` |
| 换真实向量库 | 替换 `KnowledgeBase.search()` |
| 加评审判定 | `verify` 里接第二个模型（成本翻倍，按需开） |
| 换持久化 | 实现 `Store` 协议（SQLite / Redis） |
| 用 LangGraph 重写 | 图结构直接映射，`nodes` 和条件边函数可原样复用 |
| 接入 MCP 工具 | 给 `ExpertBase.retrieve()` 换成 MCP 客户端调用 |
