# 05 · 多智能体路由（Multi-Agent Router）

一个**可运行、零依赖**的多智能体编排最小实现：把工单判给对的专家 Agent。

> 这不是又一个「调用 ChatGPT 的 demo」。
> 它想回答一个工程问题：**多智能体系统里，哪些该让模型决策、哪些必须写死？**

```bash
python examples/demo.py          # 离线跑（MockLLM，不需要 API Key）
python tests/run_all.py          # 52 个测试，全部离线
```

---

## 它做什么

一张用户工单进来，系统判定它属于哪一类，交给对应的专家 Agent 处理：

| 类型 | 专家 | 例子 |
| --- | --- | --- |
| `install` | 安装部署专家 | 「新机器怎么装？要什么环境」 |
| `usage` | 功能使用专家 | 「报表在哪个菜单」 |
| `troubleshoot` | 故障排查专家 | 「报 E1024 进不去」 |
| `fallback` | 通用兜底 | 「你好，有个问题」（信息不足） |

每个专家只拿到**本类**的知识库片段——这是路由相对「单体 Agent 全包」的核心收益。

## 编排图

```
load_memory ──► route ──(条件边)──┬─► expert_install ──────┐
                                  ├─► expert_usage ────────┤
                                  ├─► expert_troubleshoot ─┤
                                  └─► expert_fallback ─────┤
                                                           ▼
                                                       verify ──► remember ──► END
```

| 节点 | 职责 | 是否用 LLM |
| --- | --- | --- |
| `load_memory` | 取客户长期档案 + 本会话历史 | ❌ |
| **`route`** | ★ **判定类别 + 置信度** | ✅ **唯一一处模型决策** |
| `expert_*` | 检索 → 生成回答 → 抽引用 | ✅（生成） |
| `verify` | 检查引用/澄清/异常 | ❌（规则校验） |
| `remember` | 写入两级记忆 | ❌ |

## ★ 三个核心设计取舍

### ① 只有 `route` 一处让模型做决策

**为什么**：把「判断」交给模型（灵活，能处理没见过的说法），把「流程」写死（可控、可测、可审计）。

纯自主 Agent 不可控，纯规则系统不灵活——**两者之间的这个点才是生产可用的**。

### ② 置信度低于阈值就兜底，不硬分派

```python
CONFIDENCE_THRESHOLD = 0.7
```

**为什么**：分错的代价 > 承认不确定的代价。低置信度时转 `fallback` 并向用户索取补充信息。

### ③ `verify` 是独立节点，不塞进专家里

**为什么**：**生成和检查是两种能力。** 混在一起时，检查会被"我刚才生成的看起来没问题"这种惯性带偏。

`verify` 用**可判定的规则**（不调 LLM，成本为零）拦住三类问题：
- 非兜底场景**没标注引用** → 疑似编造
- 判定信息不足但**没向用户提问** → 等于没处理
- 上游异常 / 空回答

## 为什么不用 LangGraph

本项目手写了一个 **约 100 行**的状态图引擎（`router_agent/graph.py`）。

**理由**：LangGraph 的核心就是「节点 = `(state) -> update` 的函数」+「边 = 固定或条件跳转」+「一个带步数上限的循环」。**手写一遍之后，再用任何框架都不会被抽象迷惑。**

对应关系：

| LangGraph | 本项目 |
| --- | --- |
| `StateGraph` | `Graph` |
| `add_node` / `add_edge` | `add_node` / `add_edge` |
| `add_conditional_edges` | `add_conditional` |
| `compile()` | 无需编译 |
| `invoke()` | `run(state, max_steps=20)` |

**步数上限是必需的**：条件边可能成环，没有上限就会挂死（测试里专门覆盖了这条）。

## 检索：BM25 为主，混合检索留作扩展

**500 篇知识库（手写 24 + 程序生成 476）上的消融实验，核心 24 条难样本 Recall@3：**

| 策略 | Recall@3 |
| --- | ---: |
| 旧：bigram + IDF | 0.917 |
| **新：BM25（Okapi 实现）** | **0.958** ← 默认 |
| 新：TF-IDF 哈希向量 | 0.750 |
| 新：RRF 融合（BM25 + 向量） | 0.875 |
| ★ 新：默认（BM25 + rerank） | **0.958** |

### ★ 一个诚实的负面结果

**RRF 融合比 BM25 单路更差（0.875 vs 0.958），而且加权也救不回来。**

实测的权重扫描：

| BM25 权 : 向量权 | Recall@3 |
| --- | ---: |
| 1 : 1 | 0.875 |
| 4 : 1 | 0.875 |
| **8 : 1** | **0.875** |
| **1 : 0**（等于纯 BM25） | **0.958** |

**原因**：RRF 的分数是 `w/(rrf_k + rank)`，**只看名次**。只要某篇文档**只被向量召回**，即使把向量权重压到 1/8，它仍然会挤进 top-k。所以问题不是排序权重，是**弱召回路引入了错误候选**。

**★ 结论：混合检索的前提是「两路各自都有独立价值」。**
当一路明显更弱时，用它做**兜底**比做**融合**更合理。本项目默认用 BM25，`hybrid` 模式保留但不开 —— 等换成真正的语义 embedding 再打开。

### 路由先于检索的收益（500 篇库 · 核心 24 条）

| 策略 | n | Recall@3 | ★ 跨类污染率 |
| --- | ---: | ---: | ---: |
| 按类检索（路由已知） | 24 | 0.917 | **0.0%** |
| 全库检索（路由未知） | 24 | 0.917 | **48.4%** |

**库越大，污染越严重**：24 篇时 **43.1%** → 500 篇时 **48.4%**。

### ★ 另一个方法论发现：合成评估集不可靠

| 评估组 | n | Recall@3 |
| --- | ---: | ---: |
| 核心手写（含同义改写） | 24 | **0.958** |
| 程序生成（模板拼装） | 476 | ★ **1.000** |

**程序生成的 query 接近满分 —— 说明这类 query 太容易，不能反映真实难度。**
**评估集的质量决定评估的价值。** 需要人工标注、带同义改写的评估集才可信。

## 两级记忆

| 层 | 生命周期 | 用途 |
| --- | --- | --- |
| **会话记忆** | 随会话（`session_id`） | 多轮对话的上下文 |
| **客户档案** | 跨会话（按 `customer`） | 「这个客户上次问过同样的问题」 |

**为什么分开**：塞进同一个容器会导致 —— 要么短期记忆被长期污染，要么长期记忆被会话清空。

持久化留了 `Store` 接口，默认内存实现；接 SQLite/Redis 只需换一个实现。

### ★ `demo_tools.py` 演示什么

七段剧本，每段验证一个工程性质：

| 段 | 验证什么 |
| :---: | --- |
| 1 | 读操作随便调，无副作用 |
| 2 | 错误信息必须**模型可读**（给出可用列表，而不是 "failed"） |
| 3 | ★ **同一个 `idempotency_key` 调两次，只创建 1 条工单** |
| 4 | 幂等命中返回**第一次的结果**（同一个工单号） |
| 5 | 缺幂等键 → **注册表在调用前就拦住**（工具根本没执行） |
| 6 | 高风险操作：工单不存在时**直接拒绝**；缺 reason 被拦 |
| 7 | 汇总：7 个工具、工单状态变化 |

实际输出（第 3 段）：
```
第 1 次调用：已创建工单 T1001
第 2 次调用（同 key）：（幂等命中：该请求此前已处理，未重复创建）工单号 T1001
当前工单数 = 1   ← ★ 没有变成 2
第 3 次调用（新 key）：已创建工单 T1002
当前工单数 = 2   ← 这才应该 +1
```

## 工具集：读 / 写 / 高风险，三种性质

前两批只有 `kb_search`（读）和 `ask_user`（提问）—— 都是**无副作用**的，试不出工具设计里最要命的问题。
第 3 批把它扩到 **7 个工具**，第一次引入写操作和高风险操作：

| 工具 | 性质 | 关键点 |
| --- | :---: | --- |
| `kb_search` | 读 | 检索知识库 |
| `ask_user` | 读 | 模型主动追问 |
| `get_customer_history` | 读 | 查客户历史工单 |
| `get_error_code` | 读 | 查错误码字典（`enum` 之外用「不在字典中 + 可用列表」兜底） |
| `check_service_status` | 读 | 查服务健康（`service` 用 **enum** 约束 4 个值） |
| **`create_ticket`** | ★ **写** | ★ **必须传 `idempotency_key`，同 key 只创建一条** |
| **`escalate_to_human`** | ★ **高风险** | ★ **不可撤销，必须给具体理由** |

### ★ 幂等是怎么实现的

```python
class IdempotencyStore:
    def run(self, key, fn):
        if key in self._results:
            self.hits += 1
            return self._results[key], True    # 命中：返回第一次的结果，不执行
        self.misses += 1
        result = fn()
        self._results[key] = result
        return result, False
```

**三个必须说清的点**：
1. **键由调用方（Agent）生成**，服务端只负责去重
2. **键必须在重试之间保持不变**，否则去重失效
3. **命中缓存时返回第一次的结果**，不是重新执行

**实测**：同一个 key 调两次 → 只创建 **1** 条工单，第二次返回「幂等命中」并给出**同一个工单号**。

### ★ 高风险操作的三道闸

`escalate_to_human` 做了三层防护：

| 层 | 做法 |
| --- | --- |
| 描述 | 写「★ 高风险操作，不可撤销」+ 「不要一遇到不确定就转人工」 |
| 前置校验 | 工单不存在时**直接拒绝**，并列出当前可用工单号 |
| 返回 | 明确回报「此操作不可撤销」 |

### ★ 工具变多以后的代价

7 个工具意味着**每轮上下文里都有 7 份 description + schema**。
测试里专门断言了 schema 质量：

- 每个工具都有 `description` 与 `parameters`
- ★ **写操作的描述里必须出现「写操作」和「idempotency_key」**
- ★ **高风险工具的「高风险」「不可撤销」两个关键词必须出现**
- ★ **每个工具都写了「不要用它做什么」（反向边界）**
- `enum` 约束（`service` 只有 4 个合法值）

> 工具数一旦超过 20–30 个，就要考虑**分组按需挂载 / 工具检索 / MCP 按需加载**。
