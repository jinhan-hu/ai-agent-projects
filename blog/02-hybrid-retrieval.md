# RAG 混合检索：为什么纯向量不够

> 这是「从零实现 Agent」系列的第二篇。项目地址：[mini-agent-harness](https://github.com/jinhan-hu/ai-agent-projects/tree/main/04-agent-harness)

## 一个真实的检索失败

假设你做了一个企业知识库问答。用户问：

> **"XM-2000A 的保修期是多久？"**

知识库里明明有这条：

> *XM-2000A 型号产品自购买之日起提供 24 个月保修。*

但纯向量检索返回的是：

> *XM-3000 型号产品自购买之日起提供 12 个月保修。*
> *XM-1500 型号产品自购买之日起提供 18 个月保修。*
> *本公司所有型号产品均提供保修服务，具体期限见产品说明书。*

**答案就在库里，但没被召回。**

模型基于召回的错误文档，自信地回答："保修期是 12 个月。"

**这不是模型的问题，是检索的问题。**

---

## 纯向量的两个硬伤

### 硬伤一：精确标识被"语义泛化"掉了

Embedding 模型把文本压成一个稠密向量。**它的目标是"语义相近"——所以 `XM-2000A` 和 `XM-3000` 在它眼里几乎是同一个东西。**

因为这两个词的**语义**确实相近：都是"某型号产品"。

**但在业务上，这两个字符串必须被区分对待。**

同样的例子还有：

| 类别 | 例子 | 为什么向量会失败 |
| --- | --- | --- |
| 产品型号 | `XM-2000A` vs `XM-3000` | 语义都是"型号" |
| 版本号 | `v2.3.1` vs `v2.3.2` | 语义都是"版本" |
| 订单号 | `SO-2026-1031` | 训练语料里没有这种模式 |
| 人名 | 客户 `张伟` vs 员工 `张伟` | 语义完全一样 |

**★ 关键**：**Embedding 的"优点"（语义泛化）恰恰是它在这些场景下的"缺点"。**

### 硬伤二：长尾术语根本没见过

Embedding 模型是在通用语料上训练的。**你公司的内部术语、行业黑话，它没见过。**

比如一个做工业设备的公司，内部把某种故障叫"打嗝"，把某个部件叫"小狗头"。

**这些词在模型眼里是一堆随机方向——它们之间的向量距离毫无意义。**

---

## BM25 补的是什么

BM25 是一个**传统的关键词检索算法**（本质是 TF-IDF 的改进版），它只看**字面是否匹配**。

| | 向量检索 | BM25 |
| --- | --- | --- |
| 匹配依据 | 语义相似度 | **字面词频** |
| `XM-2000A` vs `XM-3000` | ❌ 几乎相同 | ✅ 完全不同 |
| `怎么退钱` vs `退款流程` | ✅ 语义相近 | ❌ 字面不重合 |
| 长尾术语 | ❌ 向量表示很差 | ✅ 字面能对上 |

**★ 一句话**：

> **向量擅长「意思像」，BM25 擅长「字面像」。**

**这两者不是替代关系，是互补关系——它们各自的失败场景，正好是对方的强项。**

## 混合检索的架构

```
                       ┌──→ 向量检索（语义）──┐
用户问题 ──→ 双路召回 ──┤                      ├──→ RRF 融合 ──→ Rerank ──→ top-k ──→ LLM
                       └──→ BM25（关键词）────┘
```

三个环节：

| 环节 | 做什么 | 关键决策 |
| --- | --- | --- |
| **双路召回** | 两路各召回 top-50 | 保留比最终需要更多的候选 |
| **融合** | 把两路结果合并成一个排序 | ★ 怎么合？见下 |
| **精排** | 对合并后的候选做精细打分 | 减少噪声，最终只留 top-5 |

---

## 融合：为什么用 RRF 而不是加权求和

最直觉的做法是加权求和：

$$
\text{score}(d) = \alpha \cdot \text{vec\_score}(d) + (1-\alpha) \cdot \text{bm25\_score}(d)
$$

**但这有个大问题：两种分数的尺度完全不同。**

- 余弦相似度：`0 ~ 1`
- BM25 分数：`0 ~ 几十`（取决于文档长度和词频）

**直接加权，BM25 会完全压过向量分数。** 你必须先归一化——而归一化方式（min-max？z-score？）本身又是个需要调参的选择。

### RRF：只看排名，不看分数

**Reciprocal Rank Fusion** 的做法是彻底绕开"分数尺度"这个问题：

$$
\text{RRF}(d) = \sum_{i=1}^{n} \frac{1}{k + \text{rank}_i(d)}
$$

其中 `rank_i(d)` 是文档 d 在第 i 路结果里的排名，`k` 通常取 60。

**举个具体例子**，k=60：

| 文档 | 向量排名 | BM25 排名 | RRF 分数 |
| --- | ---: | ---: | ---: |
| A | 1 | 未召回 | 1/61 + 0 = **0.0164** |
| B | 3 | 2 | 1/63 + 1/62 = **0.0320** |
| C | 20 | 1 | 1/80 + 1/61 = **0.0289** |

**B 排在 C 前面**——因为它在**两路里都表现良好**，而 C 虽然 BM25 第一，但向量排到 20。

**★ RRF 的精髓**：**"被两路都认可"比"被一路极力推荐"更可信。**

**而且它天然解决了归一化问题——`1/(k+rank)` 与原始分数无关，两路直接可比。**

## 为什么 Rerank 必须两段式

召回之后还要做一次精排，用 Cross-Encoder 模型。**为什么不直接用 Cross-Encoder 追求最高精度？**

**因为 Cross-Encoder 无法预建索引。**

| | Bi-Encoder（向量检索用） | Cross-Encoder（精排用） |
| --- | --- | --- |
| 输入 | query 和 doc **分别**编码 | query + doc **拼接**后编码 |
| 能否预计算 | ✅ 文档向量可离线算好存库 | ❌ 离开 query 无法单独编码 doc |
| 速度 | 毫秒级（百万文档） | 几十毫秒**每条** |
| 精度 | 中 | 高 |

**所以分工是必然的：**

- **召回阶段**：候选是**百万级** → 只有能预建索引的 Bi-Encoder / BM25 跑得动
- **精排阶段**：候选只剩**几十到上百条** → 才用得起 Cross-Encoder

**★ 不是"Rerank 想用 Cross-Encoder"，而是"只有它能用在这个位置"。**

---

## 什么时候**不要**做混合检索

**混合检索不是免费的：**

| 成本 | 说明 |
| --- | --- |
| 维护两套索引 | 向量库 + BM25 索引，都要更新 |
| 延迟增加 | 两路召回 + 融合，比单路慢 30~50% |
| 调参复杂 | k 值、召回路数、融合方式都要试 |

**所以先问三个问题：**

1. **知识库里有没有大量精确标识**（型号、订单号、人名）？→ 有 = 需要 BM25
2. **有没有内部黑话/长尾术语**？→ 有 = 需要 BM25
3. **用户的提问是否规范**（会不会用同义改写）？→ 会 = 需要向量

**三个都是"否"，纯向量可能就够了。**

**反过来，只要有一项是"是"，混合检索就是值得的。**

---

## 小结

1. **纯向量的硬伤**：精确标识被语义泛化、长尾术语没见过
2. **BM25 补的是「字面像」**：向量和 BM25 的失败场景正好互补
3. **融合用 RRF**：只看排名不看分数，天然解决尺度问题
4. **Rerank 必须两段**：Cross-Encoder 不能预建索引，只能用在候选少的阶段
5. **先问三个问题再决定要不要混合**：不是所有场景都需要
